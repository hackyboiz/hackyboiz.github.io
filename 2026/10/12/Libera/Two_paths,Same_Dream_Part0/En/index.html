1. Android IPC and Data Transfer Structure

In the Android ecosystem, apps run in separate, isolated processes by default. Therefore, to pass data from App A or Activity A to App B, you must use an IPC-based communication method, such as Intent.putExtra(“username”, “Libera”).

To understand how data is packaged and transmitted during this process, you need to be familiar with the following three key concepts.

  • Intent: An object that contains destination and action instructions, such as “Navigate to a specific screen” or “Launch a specific service.” When passing data, you use the Extra property of this Intent.
  • Extra Property: An Intent can carry not only a destination but also additional data needed to perform tasks at that destination. The Extra is the space (property) provided within the Intent to store this data.
  • Bundle: An object used to bundle and store actual data within an Intent’s Extra property. Internally, it uses a Map data structure—optimized for memory efficiency—to manage data as key-value pairs.
  • Parcel: A container (memory buffer) that serializes the data contained in a Bundle into bytes so it can be transmitted between processes.

In other words, data is grouped into a Bundle ⇒ loaded into the Extra section of an Intent ⇒ placed into a container called a Parcel and compressed (serialized) into bytes ⇒ then delivered to another process via the Binder kernel driver. This is the flow of IPC communication in Android.

The reason data must be serialized is that, in order to safely cross the memory barriers isolating processes via the Binder kernel driver, it is absolutely necessary to serialize the data according to a specific format and place it inside a Parcel container.

2. Parcel

A Parcel is a memory buffer and serialization container used in Android IPC to transfer data between processes. This buffer can hold not only primitive-type data—such as regular strings, constants, and byte arrays—but also custom objects that implement Parcelable, Android’s dedicated IPC serialization interface.

Here, Parcelable refers to a specialized data specification (interface) designed to transmit objects quickly and efficiently within the Android environment. Serializable, Java’s default serialization method, has the drawbacks of being slow and having high memory overhead due to its internal use of reflection. To address this, the Android OS introduced Parcelable, which maximizes IPC communication performance by requiring developers to explicitly specify the process of packaging and unpacking objects into bytes in their code, rather than leaving it to the system.

Additionally, Parcel provides methods (writeList, readMap, etc.) for directly reading from and writing to standard Java Collection objects such as Array, List, Map, and SparseArray. These collection data structures are important here because they have a nested structure that internally contains other Parcelable objects or sub-collections.

The process of serializing and deserializing a Parcelable object is as follows:

  • Serialization (Write): The sender overrides the writeToParcel method to write member variables to the Parcel buffer in the defined order and size.
  • Deserialization (Read): The receiver reads bytes from the data stream via the createFromParcel method to reconstruct the object in memory.

The most critical security prerequisite here is that the type, size, and order of the data written during serialization (Write) must exactly match the logic used during deserialization (Read).

This is due to the way Parcel stores data; Parcel is essentially a simple, continuous byte stream that does not separately store the boundaries of internal data. Since there are no markers indicating, “This part is an integer, and this part is a string,” the boundaries of data structures are defined solely by the order and logic specified by the developer.

Therefore, if even a single byte is read out of order or with the wrong size compared to how the sender wrote it, the meaning of all subsequent data changes completely.

3. Parcel Mismatch

When a read operation on the Parcel buffer occurs on the recipient’s side, the parser deserializes all of its contents sequentially from start to finish.

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

If you look at the image above, you can see that the outer ArrayList container holds the string “abc,” the integer 123, Parcelable (P1), and another list, List L1. Furthermore, if you look inside this List L1, you’ll see various elements—such as strings, integers, Parcelable, and Serializable—nested in layers upon layers.

In other words, when the deserialization process begins, it doesn’t simply stop after reading the outermost layer; starting with the very first element (the string “abc”), every element—all the way down to those inside the deepest Map—is deserialized in a chain reaction.

But what happens if a discrepancy arises between the “amount written” and the “amount read” due to a specific logic error or a developer’s mistake? Let’s take a look at the code below.

Parcelable Write (Transmission Logic)

public void writeToParcel(Parcel parcel, int flags) {
    parcel.writeInt(f1);
    parcel.writeByteArray(f2);
}

Parcelable Read (Receive Logic)

f1 = parcel.readInt();
if (f1 > 0) { 
    parcel.readByteArray(f2);
}

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

Looking at the vulnerable code pattern above, when sending data, the integer f1 and the byte array f2 are always serialized and written to the buffer. On the other hand, when receiving data, if the value of the integer f1 is less than or equal to 0, the readByteArray(f2) function is not executed due to the if statement, causing the entire array read operation to be skipped.

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

The photo above shows the moment when a single logic mismatch causes the parsing offset to go out of sync.

Unless an exception is thrown immediately upon encountering the first data, the Android parser does not stop and continues to attempt to parse subsequent data. However, because the remaining data from the byte array—which was left unread in the previous step—remains in the buffer, all subsequent data is parsed incorrectly starting from a completely wrong position (offset), leading to critical sequential data corruption.

4. Self-changing Bundle

This “Parcel Mismatch” issue, which appears to be a simple data corruption problem, can be exploited by hackers as a powerful weapon known as a “self-changing bundle.”

Bundle b = new Bundle();
// Fill b
Bundle c = new Bundle(b.writeToParcel()); 
// b.writeToParcel => 직렬화(Serialization)
// new Bundle() => 역직렬화(Deserialization)

A “self-changing bundle” refers to an anomalous bundle where the contents logically change (b != c) when the original bundle (b) is serialized once and then deserialized and assigned to a new bundle (c).

Let’s examine how this “magic” is used in an attack through the IPC flow: Process A (attacker) ➔ B (security verification) ➔ C (final execution).
Attacker A’s goal is to cleverly hide malicious data (e.g., intent => 42) so that the defense system B cannot detect it, pass it through, and then have it executed at the final destination, C.

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

The vulnerable package used in the attack has a mismatch error, as shown in the image above, where “only 4 bytes are read (readInt) but 8 bytes are written (writeLong).”

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

An attack scenario exploiting this vulnerability unfolds as follows.
(In the image, A(H) represents the bundle header, A0 represents the vulnerable package, and A1 represents the hidden malicious Intent.)

  1. A ➔ B Transmission and Parsing by B (TOC: Time of Check):

    A sends data to B. When B deserializes the data for inspection, readInt() is called on the first vulnerable element (A0), reading only 4 bytes.
    The maliciously placed Intent (A1), positioned immediately afterward, is not parsed as an object but is treated as simple byte array data, allowing it to successfully bypass B’s security checks.

  2. Variation During the B ➔ C Retransmission Process:

    After completing the checks, B performs deserialization again to pass the data to C. At this point, writeLong() is called in the vulnerable package, appending four meaningless zeros after the original 4-byte “0,” resulting in a total of 8 bytes being written.

  3. Parsing and Privilege Escalation in C (TOU: Time of Use):

    C deserializes the data received from B. C also calls readInt() on the vulnerable component, reading only the first 4 bytes of the 8-byte block and stopping there.
    At this very moment, the remaining 4 bytes of meaningless data generated by B are left in the parsing pointer. C mistakenly interprets these remaining 4 bytes as the key length for the next item (A1).
    As a result, the parsing position is shifted exactly, causing a byte array that was previously treated as simple data to become the target of deserialization. Through the parsing process, it is resurrected as a new, fully formed malicious Intent object, ultimately leading to critical issues such as privilege escalation.

5. Android 13 Introduces ‘Lazy Bundle’

The fundamental reason why this “Parcel Mismatch” could have become a system-wide catastrophe was the “eager deserialization” approach used up to Android 12.

In the Android 12 environment, even when querying just a single specific item within a Bundle, the entire Bundle would be deserialized all at once. In other words, even the remaining items that were not immediately needed were all parsed, converted into actual objects, and then loaded into the Map.

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

Let’s assume that P1 and P2 were inserted into the Parcel buffer (cylinder) in that order, as shown in the photo above. If a mismatch occurs in the P1 class—causing it to read less than the intended amount—reading the second item, k2, and P2 would start from the incorrect offset, corrupting the interpretation of the entire bundle. This issue was an unavoidable limitation because the boundaries of the structure were defined solely by the data (payload) and the developer’s code.

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

To address this, Google has introduced a highly intuitive and robust solution. To ensure that a mismatch in one item does not affect others, they restructured the format to include a prefix specifying the number of bytes used for serialization (prefix item length).

By specifying the length before each item in this way, even if a mismatch occurs in an internal object (P1), the parser remains unaffected and can skip exactly the number of bytes indicated in the prefix to access the correct offset for the next item (P2).

https://i.blackhat.com/EU-22/Wednesday-Briefings/EU-22-Ke-Android-Parcels-Introducing-Android-Safer-Parcel.pdf

Based on this length information, a key feature introduced in Android 13 is “Lazy Bundle.”

Now, when a Bundle is unpacked using a key, not all items are dumped and deserialized at once. For example, if a user queries only the first item, only that first item is deserialized into an actual object (Live Object), while the remaining items are stored in a Map as “Lazy Values.”

This lazy value container holds only a reference to the compressed backing Parcel (the original byte stream) and the metadata needed to deserialize each item later; deserialization occurs only when the data is actually needed.

As a result, by preventing unnecessary chained reads (Lazy) and clearly defining the boundaries (Prefix) between items, it effectively blocks malicious offset manipulation attacks, such as those involving “Self-changing Bundles,” at the source.

6. CVE-2025-48535

Earlier, we discussed why Parcel Mismatch occurs in Android 12 and how it was patched in Android 13. Since it would be a shame to cover only theoretical concepts, let’s take a look at how Parcel Mismatch actually occurs!

Even after the introduction of Lazy Bundles, a technique that triggers mismatches has emerged: the CVE-2025-48535 vulnerability. This vulnerability occurred in the Settings app, which has system privileges, and allows an attacker to execute any arbitrary Activity with system privileges. The root cause is “Creator Mismatch,” a type of mismatch we’ll be exploring.

So, what exactly is a Creator Mismatch?
It refers to a mismatch that occurs when transmitting Parcelable objects in Android because the standards of the writer and reader are completely different.

  • Serialization (Writing): Uses the writeToParcel() method of the object’s “actual runtime type.”
  • Deserialization (Reading): It uses the CREATOR static method of the “declared type” expected by the code.

Exploiting this asymmetry, the attacker sent malicious data to the Settings app not in a Intent object—a common parent class—but in a LabeledIntent object, which is a subclass of Intent.

💡 Let’s briefly touch on what a `LabeledIntent` is. A `LabeledIntent` is a “subclass” created by the framework by extending the standard `Intent` to contain custom label text and icon information to be displayed on Android screens (e.g., the share menu, app selection window, etc.). Since it is a child of `Intent`, it was able to successfully pass the system’s type-checking process. The created `LabeledIntent` object is assigned to a parent-type variable named `Intent restrictionsIntent`. Since Java allows assigning a child object to a parent variable (upcasting), this assignment passed the type check.

Let’s briefly touch on what a LabeledIntent is.

A LabeledIntent is a “subclass” created by the framework by extending the standard Intent to contain custom label text and icon information to be displayed on Android screens (e.g., the share menu, app selection window, etc.). Because it is a child of Intent, it was able to successfully pass the system’s type-checking process.

The created LabeledIntent object is assigned to a parent-type variable named Intent restrictionsIntent. Since Java allows assigning a child object to a parent variable (upcasting), this assignment passed the type check.

If you look at the actual AOSP code below, you’ll see that when LabeledIntent is serialized, it first writes the fields of its parent (Intent) and then appends its own four unique trailing fields (label, icon, etc.) before sending the data.

// frameworks/base/core/java/android/content/pm/LabeledIntent.java:28
public class LabeledIntent extends Intent {
    private String mSourcePackage;
    private int mLabelRes;
    private CharSequence mNonLocalizedLabel;
    private int mIcon;

    // :162 — Write “Parents” first, then add the four fields
    public void writeToParcel(Parcel dest, int parcelableFlags) {
        super.writeToParcel(dest, parcelableFlags);
        dest.writeString(mSourcePackage);                                   // String16
        dest.writeInt(mLabelRes);                                          
        TextUtils.writeToParcel(mNonLocalizedLabel, dest, parcelableFlags); // CharSequence
        dest.writeInt(mIcon);                                              
    }
}

One point to note here is that this first serialization—where the attacker’s app passes data to Settings—poses no problem. The class name android.content.pm.LabeledIntent is included in the Bundle, and the receiving end uses that string to select and use LabeledIntent.CREATOR. Since it’s LabeledIntent when written and LabeledIntent when read, the match is correct, and it’s read exactly up to the four-byte tail. In other words, once this step is complete, Settings has a complete LabeledIntent object with all tail values filled in, and there are no unread bytes left over.

So you might be wondering, what’s the problem? The “Creator Mismatch” error occurs next—when Settings deserializes this object and sends it to another process.

  • Sender: It calls writeToParcel(), which is an instance method, so the method for the object’s actual runtime type (LabeledIntent) is invoked. Consequently, the parent plus the four tail bytes are sent.
  • Receiving side: It uses the CREATOR of the declared type specified there. If that’s Intent.CREATOR, it reads only up to the parent schema and stops.

As a result, the four “tails” aren’t read and remain in the Parcel, getting pushed into the space reserved for other data that follows.

If you look at 0x006c, you can see that android.content.pm.LabeledIntent is embedded there as-is. This is the LabeledIntent class name—the one I mentioned earlier that determines which CREATOR runs on the receiving end—and it’s right here. Following that, starting at 0x00b4, are the fields of the parent Intent, and from 0x010c to 0x0138 are the four tails in question.

At 0x0068, you can see the length prefix; this value of 204 is functioning correctly. If there had been additional Bundle entries in this section, the next entry would be read normally regardless of what happens inside the LabeledIntent.

What the attacker secured from this Bundle was the class name set to LabeledIntent, causing the Settings app to restore the object as that type. Problems arise after this object is retrieved by the Settings app: it is deserialized again through a different channel that lacks a length prefix, yet the object remains a LabeledIntent. In other words, the four “tails” are written back exactly as they were. The “channel” referred to here is the Binder call—which we’ll see below—where Settings requests a check from PMS.

7. LaunchAnyWhere caused by a Creator Mismatch.

Before launching this LabeledIntent object, the Settings app checks whether “this is a safe destination.” However, rather than performing this check itself, it asks the system service (PMS) to verify it. In other words, the object must be sent to the PMS, and to do so, it must be deserialized again. This is precisely the point mentioned earlier where the object is deserialized and sent.

// Code that runs within the Settings process
// AppRestrictionsFragment.java:662
private Intent assertSafeToStartCustomActivity(Intent intent) {
[1] // The object selected by the attacker is passed to the PMS across the Binder boundary!
		// Serialization → Transmission → PMS deserialization → Receipt of results—the entire round trip is completed in this single line.
    ResolveInfo resolveInfo = mPackageManager.resolveActivity(
            intent, PackageManager.MATCH_DEFAULT_ONLY);                  // :668

    // ... (Interim Check Logic) ...

[2] // Normalization that converts a new Intent back to a plaintext Intent with a runtime type.
		// There is a normalization code, but it's executed only after all the checks are complete.
    final Intent vettedIntent = new Intent(intent);                      // :683
    vettedIntent.setComponent(activityInfo.getComponentName());          // :684
    vettedIntent.setPackage(activityInfo.packageName);                   // :685
    return vettedIntent;
}

The resolveActivity method called at [1] in the code above communicates internally with the system service (PMS) via AIDL. Settings serializes an object and sends it to PMS, then receives the resolution result (ResolveInfo) from PMS. The Binder interface called at this point looks like this:

// frameworks/base/core/java/android/content/pm/IPackageManager.aidl:133
ResolveInfo resolveIntent(in Intent intent, String resolvedType, long flags, int userId);

Following the single in Intent intent parameter, three parameters—string, long, int—are waiting in sequence. When the Stub (receiver) reads the parameters in order, it is precisely at this point that the trailing fields left in the buffer are pushed into the slots for the subsequent parameters and parsed!

This call is sent as a single Binder transaction. The four arguments listed in the declaration above are packed sequentially into a single Parcel, which passes through the kernel Binder driver, and the receiving Stub extracts and reads them in the same order. AIDL is the declaration that specifies this order, but it is actually this Parcel that crosses the process boundary.

Inside the Bundle, each item was prefixed with its length, so it worked fine, but the arguments in this Parcel are written sequentially after in Intent as String, long, int without any prefixes. That’s why a problem occurs as soon as a mismatch happens.

Let’s take a look at what the transaction Parcel actually looks like.

There are two key points here. The writing side wrote up to 0x0088 in arg0, but the reading side’s Intent.CREATOR starts reading from 0x005c—in other words, the 44-byte gap between these two points is where the mismatch occurs.

Let’s summarize in a table how this offset shift causes the values to become distorted.

AIDL Arguments The value intended for “Settings” The value actually read by the PMS (offset drift) In terms of offset,
intent Attacker Intent Attacker Intent (So far, so good) 0x0000~0x005c
resolvedType null “text/plain” ➔ mSourcePackage 0x005c
flags 0x10000 0x0000000100010000 ➔ The lower 32 bits represent mLabelRes, and the upper 32 bits represent the TextUtils marker 0x0078~0x0080
userId 0 -1 ➔ Label string length field 0x0080

As a result, none of the system’s intended validation conditions function as intended, and they are replaced with flags and conditions manipulated by the attacker. Based on these manipulated values, the resolveInfo returned by PMS points to the attacker’s package, causing the Settings app to mistakenly believe it is safe and execute it with system privileges (System UID).

So, how exactly was the vulnerability patched?

The patch was implemented by moving the normalization code to the front of the call, and the vulnerability was fixed with just a single line of code. The new Intent(intent) statement in the original code [2] served to preserve the field values while reverting the runtime type to plain Intent—and this code was simply moved to the front.

private Intent assertSafeToStartCustomActivity(Intent intent) {
[1] // Moving normalization to before the Binder boundary (removing subclass tag dictionaries)
+    final Intent vettedIntent = new Intent(intent);
     
     ResolveInfo resolveInfo = mPackageManager.resolveActivity(
[2] // The items to be inspected will also be replaced with normalized copies rather than the originals
-            intent, PackageManager.MATCH_DEFAULT_ONLY);   // Removed.
+            vettedIntent, PackageManager.MATCH_DEFAULT_ONLY);

     // ... 
     // Remove any normalization that was done late
-    final Intent vettedIntent = new Intent(intent);       // Removed.
     vettedIntent.setComponent(activityInfo.getComponentName());
     vettedIntent.setPackage(activityInfo.packageName);
     return vettedIntent;
 }

Since normalization is now performed “before” crossing the Binder boundary, any tail fields added by subclasses are thoroughly removed in advance. This ensures that only the plaintext Intent schema remains during serialization, thereby preventing a Creator Mismatch from occurring.
